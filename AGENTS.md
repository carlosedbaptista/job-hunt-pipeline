# Job Hunt Pipeline — AGENTS.md

## Project Overview

**Goal**: Automated job search and evaluation pipeline for AI / Automation / Data Engineering roles in Switzerland (Zurich/Zug). Ingests jobs from Adzuna and Gmail alerts, deduplicates, fills in missing descriptions, scores fit with the Kimi LLM, and delivers a daily digest, dashboard and alerts.

**Runtime**: GitHub Actions, 2x/day (05:00 and 12:00 UTC). No local server.

**AI provider**: Kimi (Moonshot) API, for the pipeline runtime and the development assistant alike (Kimi CLI). This is a deliberate decision: do NOT migrate the pipeline to any other provider.

---

## Technical Stack (real, as deployed)

- **Language**: Python 3.11
- **LLM**: Kimi API, model `kimi-k2.6` (fallback configurable via `KIMI_MODEL_FALLBACK`). `moonshot-v1-*` and `kimi-k2.5` sunset on 2026-08-31, never use them.
- **Job sources**: Adzuna API (`agents/adzuna_ingestor.py`), Gmail IMAP with App Password (`src/email_ingestor.py`)
- **Storage**: SQLite `tracker/jobs.db` (seen jobs, dedup), JSON artifacts in `digests/` and `data/`
- **Evaluation history**: `data/history/evaluations_YYYYMMDD.json` (appended every run)
- **Dashboard**: static HTML generated by `src/dashboard.py`, published via GitHub Pages. Fully static (no backend/write path): shows an "Application" column joined from `tracker/jobs.db`'s `applications` table by normalized company+title. In-dashboard dedup is by normalized company+title (NOT URL -- the same posting arrives with different tracking URLs per source), and manual evaluations are merged FIRST so a manual re-evaluation always wins over the older history entry. A REVIEW/APPLY job with no tracked record and 10+ days old is shown as "No action" -- inferred, not an explicit user action (marking every skipped job would be too much friction). Actually recording "applied" or a response still only happens via `.github/workflows/track-application.yml`.
- **Notifications**: Gmail SMTP (digest email + high-score alerts)
- **Tests**: `tests/` (pytest, mocked LLM -- no API calls). `test_scoring_consistency.py` is the consistency suite born from the 2026-08-17 audit; `test_ingestion_quality.py` covers what the scorer is *fed* (alert-card parsing, in-batch dedup, description enrichment) and comes from the 2026-08-21 ingestion audit. Install with `pip install -r requirements-dev.txt`, run `python -m pytest tests/` before touching scoring, dedup or parsing logic -- and `.github/workflows/tests.yml` now runs it on every push and PR, so this is no longer on the honour system. `scripts/smoke_kimi_brain.py` (gitignored) re-probes the real model against 10 controlled synthetic postings when the prompt changes.
- **Testing the pipeline on demand**: `job-hunt-scheduler.yml`'s manual run takes three inputs, all off by default and never set by the cron runs. `skip_ingestion` reuses the batch already fetched (Adzuna's free tier is 100 calls/day and one run spends 18, so on a day of testing there is no budget for a second fetch); `reevaluate` re-scores jobs already marked seen (`REEVALUATE_ALL`, without which a second run finds nothing new); `max_evaluations` caps the jobs evaluated for that run (in agent mode each job can cost up to `AGENT_MAX_ITERATIONS` LLM calls) -- use 3-5 when testing, because `reevaluate` otherwise re-scores 30 jobs each time. Note a blank input arrives as an EMPTY STRING, not as unset, which is why `utils.max_evaluations_per_run()` treats empty and non-numeric as the default instead of crashing on `int("")`.
- **CI**: `.github/workflows/job-hunt-scheduler.yml` (daily pipeline), `.github/workflows/tests.yml` (pytest + `compileall` on push/PR, no secrets exposed), `.github/workflows/add-job.yml` (manual evaluation -- also generates CV/CL automatically when the match is >= `THRESHOLD_APPLY`, via the same `agents/doc_generator.generate_docs_for_job()` the daily pipeline uses), `.github/workflows/track-application.yml` (manual: record that you applied, or a recruiter response, via `agents/tracker_updater.py`)
- Re-running "Add Job" for a posting you already evaluated REPLACES the old record (matched by normalized company+title, same as the dedup hash) instead of appending a duplicate -- the old score/reasoning is gone once replaced, by design.
- **What is tailored per job, and what is deliberately not.** The cover letter is written per posting. The CV's PROFILE SUMMARY is generated per posting and is given the exact `role` string with a hard rule never to restate it (the header said "AI & Automation Developer Intern" while the summary underneath called him an "Automation developer" -- a document disagreeing with itself). SKILLS are REORDERED so the stack the posting names comes first (`_order_skills_for_job`, reordering only, nothing added or dropped). EXPERIENCE BULLETS are never rewritten per job: that is precisely where the model invented "a guardrail firing too late in the sequence", and a fabrication there is about his employment history.
- **Four files are generated, but only the .docx are delivered.** `DELIVER_FORMATS` (default `.docx`) controls what is attached to the e-mail; everything generated still goes to Drive. The candidate's reasoning, 2026-08-24: the file he opens is the one he needs to correct, and the system will not always be right. The PDF remains the copy an employer receives -- fixed layout, not editable by accident, the norm for applications -- and sits in Drive one click away. Note the .docx is LARGER, not smaller, so this is about editability, never weight.
- **Every application produces four files, not two**: `CV_*.pdf` / `CL_*.pdf` (what gets sent: fixed layout, nobody edits them by accident) and `CV_*.docx` / `CL_*.docx` (the working copies, added 2026-08-23 at the candidate's request -- "the system will not be perfect, so I need the docx to fix the errors"). All four go to Drive and to the e-mail. The .docx is UTF-8 and must NOT pass through `_safe_text`, which exists only for the PDF's Latin-1 core fonts. Note the .docx is LARGER, not smaller (letter 2.9 KB as PDF against 38 KB; CV 28 KB against 63 KB) -- the value is editability, never weight.
- **How a generated CV/CL reaches the candidate -- by e-mail, not Drive**: `doc_generator` attaches both PDFs and mails them to `GMAIL_RECIPIENT` (`_email_docs_to_candidate`, reusing `email_notifier.send_email(..., attachments=[...])`). It goes to the candidate only, never a recruiter, so the "never submit without approval" rule holds. This exists because the two alternatives are both closed: the repo is PUBLIC so the PDFs can be neither committed nor uploaded as an Actions artifact (a 90-day artifact on a public repo is downloadable by any authenticated GitHub user, and the PDFs carry name, phone, e-mail, LinkedIn, permit and photo -- that upload was REMOVED), and Google Drive has never worked. Verified again on 2026-08-23: without the e-mail path a generated document died with the runner.
- **Google Drive works, via OAuth2 with the `drive.file` scope** (set up 2026-08-23). The Service Account path is dead by construction and kept only as a fallback: Google reports a Service Account's quota as `{"limit": "0"}`, so it owns no bytes and every upload into a personal Drive answers 403 `storageQuotaExceeded`. Sharing the folder with it grants the right to enter, never to store; only a paid Workspace Shared Drive would work. OAuth2 makes the candidate the owner (15 GB). The scope is `drive.file`, NOT `drive`, because the refresh token lives in a GitHub Secret: a leak then costs the job PDFs he already sends to recruiters instead of his entire personal Drive. Consequence to remember: **a folder created by hand in the browser is invisible to the app**, so `_resolve_root_folder()` probes `GDRIVE_PARENT_FOLDER_ID` for reachability and falls back to finding-or-creating its own `GDRIVE_ROOT_FOLDER_NAME` root. Structure is `Job Hunt Pipeline / {Company} - {Title} / CV+CL`. `config/oauth2_client_secret.json` (gitignored) and `GDRIVE_REFRESH_TOKEN_B64` are what make it run; re-mint both with `python config/setup_oauth2.py`.

## Pipeline flow (as executed by CI)

1. `agents/adzuna_ingestor.py` — fetch Adzuna jobs (strips query strings from URLs: they embed the app_id). 18 queries against ONE location (Zurich) with `ADZUNA_DISTANCE_KM=30`, which reaches Zug and Winterthur in the same call. The Zurich+Zug pass it replaced spent half the free tier on Zug for 4 distinct jobs in 84 days (measured 2026-08-23). `results_per_page` is Adzuna's maximum of 50: page size does not change the call count. Budget: 18 x 1 x 2 runs = 36/day, plus up to 24 from the enricher, against a free tier of 100 — `tests/test_adzuna_targeting.py` asserts this, so redo the arithmetic there before adding a query or a location.. Queries are overridable via `ADZUNA_QUERIES`; keep the list at 12 or redo the quota arithmetic in the comment there
2. `src/email_ingestor.py` — fetch Gmail alerts (IMAP UIDs, `continue-on-error`)
3. `agents/email_parser_local.py` — parse job emails locally (regex + BeautifulSoup, no API)
3b. `agents/description_enricher.py` — fills missing descriptions from Adzuna, then recovers TRUNCATED ones from the employer's ATS via `agents/posting_resolver.py`
3c. `src/utils.is_off_target_title` — a cheap relevance gate applied in `unified_ingestor` BEFORE the cost cap. Broadening the Adzuna queries multiplied intake by 7.7 and brought marketing, sales and M&A roles with it (49 of 56 titles on 2026-08-23), each costing an LLM call before being correctly SKIPped. A keyword blacklist was measured and REJECTED: ranked by mean score the worst keywords were `praktikum` and `werkstudent`, the German words for internship, which would have deleted the entire German funnel. The gate is a CONJUNCTION instead -- a non-technical FUNCTION with no technical term anywhere in the title -- and is validated against all 278 scored titles: it drops 13% and the highest score among them is 35. `tests/test_relevance_gate.py` re-derives that guarantee from the committed history rather than trusting the comment.
4. `src/unified_ingestor.py` — merge sources, in-batch dedup, then **cross-run dedup via `src/deduplicator.filter_new_jobs` (SQLite, 21-day retention)**. Jobs are then sorted by description length before the cap: sources arrive e-mail-first and the cap slices the FIRST n, so alert cards carrying 0 characters were systematically eating the budget ahead of Adzuna teasers that `posting_resolver` could expand into a real decision. The cost cap is applied HERE, before marking: jobs beyond `MAX_EVALUATIONS_PER_RUN` stay *unseen* and resurface next run as a queue (pre-audit behaviour marked everything seen and silently swallowed jobs 31+ forever)
5. `agents/description_enricher.py` — for jobs still under `MIN_DESCRIPTION_CHARS`, look the same posting up on Adzuna and attach the real description (`continue-on-error`; budget `ENRICH_MAX_LOOKUPS`, default 12)
6. `agents/decision_agent.py` -- evaluate each new job with Kimi (capped by `MAX_EVALUATIONS_PER_RUN`, default 30). `EVALUATION_MODE=agent` (what the scheduled workflow sets) runs a tool-using agent that investigates each job and decides; `rules` (the default) delegates to the unchanged `agents/job_evaluator.py`
7. `agents/digest_generator.py` — build digest (called directly; the `week4_pipeline.py --digest-only` wrapper was a banner and a subprocess call, removed 2026-08-23)
8. `src/dashboard.py` — regenerate dashboard
9. `agents/orchestrator_agent.py` — the run-level judgement layer, one workflow step replacing the three fixed steps that used to sit here. `ORCHESTRATION_MODE=rules` (the default) runs the legacy chain via subprocess in the old order, failure-tolerant: `agents/doc_generator.py` (tailored CV/CL for APPLY jobs, mailed to the candidate as attachments; prints a one-line count even when nothing qualifies, because silence in that step used to be indistinguishable from a crash), then `agents/high_score_alert.py` (alert once per job >= 85, dedup in `digests/alerted_jobs.json`), then `agents/followup_sender.py` (for `applications` rows with no response after 7+ days, drafts a follow-up with Kimi and emails the **draft to the candidate** (`GMAIL_RECIPIENT`), never to the recruiter; the candidate reviews and forwards it manually). `agent` mode (what the scheduled workflow sets) lets a tool-using LLM decide the same things plus bounded re-scores of stale REVIEW jobs, with the legacy chain as its coded fallback -- see "The orchestrator layer (2026-08-24)". Exits 0 in both modes and runs `continue-on-error`, so it never blocks the commit step.
10. `agents/email_notifier.py` — send digest email (`if: always()`, deliberately kept out of the orchestrator: notification safety is not a judgement call)
11. Commit `data/raw_jobs/`, `data/history/`, `digests/` (which now also picks up `orchestrator_log_*.json`) -- and `tracker/jobs.db` **only when the evaluator step succeeded**. `unified_ingestor` marks jobs seen BEFORE scoring, so committing the DB after a failed evaluation (no Kimi credits) would suppress those jobs for the whole 21-day retention: a billing lapse silently destroying three weeks of discovery. All three pushing workflows share the `job-hunt-repo-write` concurrency group (jobs.db is binary and cannot be merged) and push with rebase-and-retry.

## Scoring Philosophy (the why -- not obvious from code alone)

- **Role shape beats checklist match.** Ownership from day one, building vs. maintaining, hands-on agentic-AI work matter more than a perfect skills/domain checklist. Calibration anchor: the 'AI Platform Engineer Intern' at a small regulated investment firm, rated 100/APPLY by the candidate himself.
- **Deliberate career changer, open to unfamiliar domains** (finance, healthcare, retail): lack of domain experience is a soft gap, never a penalty when the technical/functional role matches.
- **Hard requirements are NOT domain gaps.** A mandatory fluent/native language beyond English (his German level lives in `language_levels`; A2 as of 2026-08-23), wrong permit, or ineligible location is a hard eligibility blocker -> automatic SKIP, no exception, however strong the rest of the match. An otherwise-perfect job he's disqualified from is noise, not signal. A soft mention ('German is a plus', up to B1 acceptable) is a minor signal, never a blocker. The INTERMEDIATE zone ('working/professional proficiency' -- every CEFR level above his own and below C1, derived by `utils.levels_above`, so B1 and B2 at A2) is neither: never a blocker, but APPLY is capped at REVIEW so he judges case by case and the system never auto-generates CV/CL for it (2026-08-17 product decision).
- **The score is the source of truth for ranking, but decisions are always derived locally, never trusted from the model's freeform field** -- and a real hard blocker caps the decision at SKIP regardless of score (the score stays visible for information). On 2026-08-24 this rule evolved with the agent decision layer (see the section below): in agent mode the agent proposes AND decides, but inside a fenced area -- it chooses its evidence and commits through a mandatory `record_decision` tool, then code re-applies every rail before the record is stored. `utils.effective_decision()` remains the fence: hard-blocker SKIP lock, low-confidence APPLY-to-REVIEW caps, score sanitised to int 0-100, and no decision within the iteration cap means ERROR, never a fabricated number. The final `decision` field is still derived locally; what changed is who drafts it.
- **Concerns surface at every tier, with correct severity**: real blockers render with ⛔ and the "Blocker: " prefix; minor notes get light visual weight. Never lump them together.
- **Scoring is input, not gospel**: the user can override any decision (manual re-evaluation replaces the record).

## Scoring (mechanics)

- Thresholds are defined ONCE in `src/utils.py`: `THRESHOLD_APPLY=80`, `THRESHOLD_REVIEW=70` (env-overridable). All consumers import from there. Never hardcode 80/70 elsewhere.
- Every consumer derives the decision via `utils.effective_decision(ev)` (evaluator/decision agent, digest, alerts, doc_generator; the dashboard gets it precomputed per job as `_has_blocker`/`_insufficient`/`_lang_gap`): thresholds on the sanitized score, then the hard-blocker lock, then the low-confidence caps (`insufficient_info`, description < 200 chars; `language_gap_intermediate`, the B2/working-proficiency zone -- both cap APPLY at REVIEW so neither a bare title nor an above-his-level language ask ever auto-generates CV/CL).
- The model returns a structured `hard_blockers` list separate from soft `concerns` ('Blocker: '-prefixed concerns remain as the backward-compat path for old records). Spurious "Blocker: None ..." entries are filtered by `utils.is_spurious_blocker` -- the model uses the prefix even to say there is NO blocker, and taking it literally would SKIP the best jobs.
- **Recovering the full posting: `agents/posting_resolver.py`** (added 2026-08-23, runs inside `description_enricher.py`). Employers mostly do not host their own postings, they use an ATS, and every major ATS publishes a public JSON board with the complete text and no bot protection. So the resolver guesses the board slug from the company name and matches the title across Greenhouse, Lever, Ashby, SmartRecruiters, Recruitee, Workable and Personio. **Measured hit rate: 40%** over 40 real postings; startups on Ashby/Lever resolve, enterprises on Workday/SuccessFactors do not, and "Job-Room"-style aggregator names are skipped because Adzuna puts the source board in the company field. Two rules keep it honest and are pinned by tests: a provider counts only if the payload VALIDATES as a board (Personio returns 200 with the same 1.6 MB marketing page for any slug, invented ones included), and a title match below 0.78 is REJECTED (feeding the evaluator another job's requirements is worse than feeding it nothing). A miss is the normal case: the job keeps its teaser and stays capped at REVIEW. Costs no Adzuna quota, only runner time (~2 min for 30 jobs; boards are cached per company).
- **The biggest blind spot, and it is structural: Adzuna truncates every description to 500 characters.** Measured 2026-08-23 over every record ever stored: 917 of 917, all cut mid-sentence. What survives is the opening pitch; what is lost is the requirements list, which is where the disqualifiers are. The Avaloq "AI Software Engineer" posting scored **82/APPLY on its 500-char teaser and 58/SKIP on the full text**, which demands 5 years full-stack, 3 years applied ML and a B.Sc. The model was never wrong -- it was handed 12% of the posting. `MIN_DESCRIPTION_CHARS=200` did not catch it because 500 chars looks like a real description, so `utils.is_truncated_description` is now its own signal: it feeds `insufficient_info` (capping the decision at REVIEW, so no CV/CL is generated off a teaser), it adds an explicit "requirements were not visible" concern, and it warns the model in the prompt so it stops scoring marketing copy with confidence. **The full text is not reachable automatically**: the Adzuna details page is JavaScript-rendered with no outbound link in the HTML, its /land/ and /apply/ URLs answer 403, and employer sites (avaloq.com) 403 a runner directly. Paste the real posting into the "Add Job" workflow for a trustworthy score -- that path is proven and takes the pasted text over the URL.
- `agents/job_evaluator.py` scans the FULL description deterministically in two tiers (`detect_language_requirement_tier`: hard = fluent/native/C1-C2/verhandlungssicher; intermediate = working/professional proficiency, B2) and injects the evidence snippet into the prompt with tier-appropriate instructions. Postings longer than the window are excerpted head(2/3)+tail(1/3) via `_excerpt()` -- Swiss requirement blocks live at the END of long postings: before the 2026-08-17 audit the window was a 1500-char head, and a C1-German clause past char 1500 invisibly flipped an auto-SKIP job to 96/APPLY; later the same day a 'working proficiency in German' clause past char 4000 let a job score 92/APPLY with zero language signal.
- The prompt includes today's date (grounds timeline reasoning: notice period vs start date -- the model once invented a "16+ months away" blocker for a start 2 months out) and counts fully-remote-within-Switzerland as Zurich-area.
- **Feedback loop (2026-08-24)**: APPLY-tier evaluations are recorded in `applications` as `status='recommended'` (score kept, `date_applied` NULL) by `job_evaluator.main()`, `decision_agent.py` and `add_job.py`. Only the manual `track-application` action promotes a row to `'sent'` -- that separation is deliberate: outcomes are measured ONLY over jobs actually applied to, or the scorer would learn from applications that never happened. `tracker_updater.get_outcome_summary()` aggregates the evidence and `job_evaluator.load_outcome_calibration()` appends it to the system prompt every run ("jobs you scored 80+ earned N responses, K interviews..."). `followup_sender` only ever touches `status='sent'` rows -- a recommendation must never trigger a follow-up draft. The dashboard renders `recommended` as "Recommended" (distinct from "Applied"/responses).
- **Switching models is a GitHub UI change, not a code change**: set the repository VARIABLE `KIMI_MODEL` (Settings -> Secrets and variables -> Actions -> Variables). Unset means `kimi-k2.6`. Note an undefined `vars.X` arrives as an EMPTY STRING, which is why `kimi_client._model_from_env` treats empty as unset -- otherwise every call would ask for a model named "".
- **kimi-k3 was re-measured fairly on 2026-08-24 and still shows no gain.** The 2026-08-23 comparison was invalid: the thinking guard read `startswith("kimi-k2")`, so k3 kept reasoning into a 1000-token budget and 8 of 9 calls died on JSONDecodeError. With the guard fixed, k3 makes zero errors and both models get 3/3 on the ground-truth cases. But k3 is noisier (spread 10 vs 7) and less conservative exactly where it matters: on the Avaloq posting, which demands five years of experience, k2.6 scores 45-52 while k3 scores 58-68 -- one sample two points below REVIEW. For a candidate who does not want to see jobs he cannot get, that is the wrong direction.
- **Do not switch models without re-running the comparison.** Both `kimi-k2.6` and `kimi-k3` refuse every temperature but 1, so a newer model does NOT buy determinism. On three ground-truth cases x three samples, both agreed with the expected decision 3/3, but k3 was noisier (mean spread 8.3 vs 5.3) and less conservative on the blind case, where one sample reached 78/REVIEW against k2.6's steady 65-68. No reason to move. The sample is small, so treat it as "no evidence of improvement", not as proof k3 is worse. What the exercise DID find: `_try_model` disabled thinking only for `startswith("kimi-k2")`, so k3 kept reasoning into the 1000-token budget and 8 of 9 calls died on JSONDecodeError. The guard now covers the whole `kimi-` family -- without it, any model switch looks catastrophic for reasons that have nothing to do with the model.
- **Score noise is real, unfixable by parameter, and bought off only at the boundaries.** Measured 2026-08-23, five identical calls per condition on one posting: truncated text gave 65/68/68/65/65 (spread 3), full text gave 55/55/55/35/45 (spread 20). Temperature cannot help -- `kimi-k2.6` rejects every value with *"invalid temperature: only 1 is allowed for this model"*. It mostly does not matter (all ten samples still agreed on SKIP), but on a threshold it decides everything: at 80 the same job is APPLY or REVIEW depending on which sample arrived, and APPLY is what generates a CV. So `job_evaluator._is_borderline` re-scores only within `BORDERLINE_BAND` (8, about one standard deviation) of either threshold and keeps the MEDIAN of three -- along with that sample's reasoning, so the number and the explanation always match. Measured cost: 14% of a real run (4 of 29 jobs), 8 extra calls. `BORDERLINE_SAMPLES=0` disables it; the test suite sets that in conftest.
- Score sanitisation: coerced to int, clamped to 0-100 (a string "85" used to crash into ERROR; 120 passed as APPLY). A missing/unparseable score is an ERROR, never a silent default 50. API failures produce `decision: "ERROR"`, `score: null`, excluded from rankings and metrics, reported separately. NEVER fabricate a score.
- If ALL evaluations in a run fail, the evaluator exits 1 to fail the workflow loudly (usually: no Kimi credits). Same if `config/candidate_profile.json` is missing/invalid: main() exits 1 rather than silently scoring the whole run against the generic fallback profile.
- **Language calibration is derived, never hardcoded.** `candidate_profile.json` carries `language_levels` (e.g. `{"german": "A2"}`); `utils.candidate_language_level` reads it and `utils.levels_above` computes the intermediate band as *every CEFR level above his own and below C1*. For A2 that is B1 and B2; at B1 it narrows to B2 alone. The prompt text, the pipeline-note wording and the deterministic tier regex all interpolate from it. This closed a real regression: the prompt said "his German is B1" while the CV said A2, and the intermediate band was the fixed set `{B2}`, so a "German B1 required" posting read as a *soft* mention when it was a genuine gap. An unset level falls back to the weakest, which over-reports gaps rather than hiding them -- the safe direction.
- **The scorer sees the target role, not just the current one.** `target_role` in the profile is injected as "Looking for (score fit to THIS, not to his current job)". Without it the model matched postings against his current job title, which is precisely what he is trying to move on from.
- `job_evaluator.py` asks the model for `detected_company`/`detected_title`/`detected_location` and backfills any field the caller left `"Unknown"` -- manually-added jobs (`add_job.py`) had no location-extraction logic at all before this.

## The agent decision layer (2026-08-24)

The evaluation stage is now `agents/decision_agent.py`, a drop-in replacement for the `agents/job_evaluator.py` step with the same I/O contract: reads `digests/new_jobs_latest.json`, writes `digests/job_evaluations_latest.json`, appends `data/history/evaluations_*.json`, records APPLY-tier jobs in the tracker as `recommended`, exits 1 when every evaluation fails. Which brain runs is a switch, not a fork: `EVALUATION_MODE=rules` (the default) delegates to the unchanged `job_evaluator.main()`; `agent` runs a tool-using agent. The scheduled workflow calls `decision_agent.py` with `EVALUATION_MODE: agent`.

- **What the agent is.** Per job, `run_agent` (`src/agent_runtime.py`) drives a bounded tool-calling loop over the new `KimiClient.chat_completion(messages, model=None, max_tokens=1000, response_format=None, temperature=None, tools=None, tool_choice=None)`, which returns `{'content', 'tool_calls', 'usage', 'model'}`. `chat()` keeps its exact old signature and still returns the content string; `thinking: disabled` stays forced for `kimi-*` models. The loop caps at `AGENT_MAX_ITERATIONS` (default 8) iterations and 2000 tokens per call and reports `stopped_reason` as `final` / `iteration_cap` / `error`. An `iteration_cap` with no `record_decision` earns one reserved finalization call ordering the model to commit with what it has -- the five informational tools once filled a 5-iteration cap and starved the terminal call three times in a single run (2026-08-25, identical traces). A tool exception is returned to the model as error content, never raised, so one bad tool call cannot kill the run. Tools are declared as a `Tool` dataclass: `name`, `description`, `parameters` (JSON Schema), `function`.
- **The tools wrap EXISTING deterministic code, imported, not duplicated.** `get_posting_text` returns the full posting text plus the `utils.is_truncated_description()` verdict, so the agent knows when it is reading a teaser. `check_language_requirement` runs the evaluator's deterministic two-tier CEFR detector over the full text and returns the evidence lines. `get_candidate_profile` and `get_outcome_calibration` hand it the profile and `tracker_updater.get_outcome_summary()` (what the jobs scored 80+ actually earned). `search_past_evaluations` looks up similar jobs over the committed `data/history/evaluations_*.json`. `record_decision(score, decision, rationale, concerns, hard_blockers, language_requirement)` is mandatory and terminal, the only way out of the loop. Records carry the evaluator's schema plus `agent_rationale`, `agent_decision` (what the agent proposed) and `agent_trace` (every tool call made).
- **What stays in code, and why -- the fence is the point.** After `record_decision`, code re-applies every rail, each one bought by a recorded incident:
  - The deterministic language detector still wins: a "hard" tier verdict forces a hard blocker even when `record_decision` omits it. The incident is the 2026-08-17 one: a C1-German clause past the excerpt window invisibly flipped an auto-SKIP job to 96/APPLY. The agent reads the same detector through a tool, but a model can ignore evidence; code cannot be argued with.
  - The spurious-blocker filter still runs (`utils.is_spurious_blocker`): the model uses the "Blocker: " prefix even to say there is NO blocker, and taking that literally would SKIP the best jobs.
  - The score is sanitised to int 0-100, else ERROR: a string "85" used to crash into ERROR; 120 passed as APPLY.
  - The final `decision` field is still `utils.effective_decision(record)`: hard-blocker SKIP lock, plus the truncated/insufficient-text and intermediate-language APPLY-to-REVIEW caps. Those caps are the Avaloq incident (82/APPLY on a 500-char teaser, 58/SKIP on the full text) and the 2026-08-21 finding that 169 of 190 early records were blind title-only scores given with confidence. The agent can propose APPLY; it cannot make a teaser trustworthy, and an above-his-level language ask still never auto-generates CV/CL.
  - No `record_decision` within the iteration cap AND the reserved finalization call, or a runtime error, is an ERROR record, never a fabricated score. Same rule as rules mode, same reason.
  - Jobs under `MIN_DESCRIPTION_CHARS` never reach the agent: NOT_EVALUATED, no API call spent.
- **The borderline median-of-3 does NOT apply in agent mode.** That mechanism buys off threshold noise by re-sampling (measured spread of 20 on byte-identical input; at 80 the same job is APPLY or REVIEW depending on which sample arrived, and APPLY is what generates a CV). The agent investigates instead of re-sampling: its score arrives with the evidence attached, which is the same problem solved the other way. Median-of-3 stays on in rules mode.
- **Cost arithmetic.** Rules mode is 1 call per job (+2 borderline), capped at 30 jobs. Agent mode is typically 5-6 calls per job (five investigations + the terminal call; worst case the 8-iteration cap plus the finalization nudge), so up to ~270 calls per run and ~540/day at two runs, bounded by `AGENT_MAX_ITERATIONS` x `MAX_EVALUATIONS_PER_RUN` and the unchanged 2s sleep between calls.
- **Unchanged, and worth restating because the word "agent" invites scope creep**: the agent never submits an application (CV/CL and follow-up drafts still go only to the candidate), the provider is still Kimi only (`kimi-k2.6`), there are no new third-party dependencies, and all tests mock the LLM.

## The orchestrator layer (2026-08-24)

The three fixed steps that used to end the daily run (docs, high-score alerts, follow-up drafts) are now one step, `agents/orchestrator_agent.py`, with the same switch-not-a-fork shape as the evaluator: `ORCHESTRATION_MODE=rules` (the default) runs the three legacy scripts via subprocess in the old order (`doc_generator` -> `high_score_alert` -> `followup_sender`), failure-tolerant, byte-for-byte the pre-orchestrator behavior; `agent` runs one bounded tool-calling conversation that decides what the run needs. The scheduled workflow sets `ORCHESTRATION_MODE: agent`. The step exits 0 in both modes, so it can never block the commit step.

- **What the orchestrator owns**: documents for APPLY jobs, the >= 85 alert, follow-up drafts for stale applications, re-scoring recent REVIEW-band jobs when budget remains, and its own failure handling.
- **What it deliberately does NOT own.** The ingest -> decide -> digest spine stays fixed YAML steps, because that sequence is the pipeline, not a judgement call. `email_notifier` stays a separate `if: always()` step for the same reason: notification safety is not a judgement call, and an agent that could decide not to notify is a worse failure mode than an agent that crashes.
- **The tools wrap existing code, imported, not duplicated** (the decision agent's pattern). `get_run_state` reads `digests/job_evaluations_latest.json` and returns counts by effective decision, the digest summary, the error tail, stale applications and a `fresh` flag. `generate_docs` wraps doc_generator and REFUSES when the evaluations file is not from today. `send_high_score_alerts` and `draft_followups` wrap the two legacy mailers. `reevaluate_borderline(max_jobs)` re-scores recent REVIEW-band jobs through `decision_agent.evaluate_job()`. `finish_run(summary, rationale)` is mandatory and terminal, the only way out of the loop.
- **Four rails, all in code.**
  - *Freshness guard.* On a failed evaluator run the evaluations file is yesterday's, and generating docs from it spends real Kimi calls on CV/CLs that already exist. The workflow step is therefore deliberately not `if: always()`, and `generate_docs` re-checks the date in code for the paths the workflow gate cannot see (hand runs, `skip_ingestion` testing).
  - *Guaranteed floor.* Any failure (client error, iteration cap reached, no `finish_run`) runs the legacy chain automatically and records `fallback_used: true`. A bad orchestrator day degrades to exactly the old behavior: docs, alerts and follow-ups can be late or expensive, never skipped.
  - *Two budget caps.* `ORCHESTRATOR_MAX_ITERATIONS` (default 8) bounds the conversation; `reevaluate_borderline` is hard-capped in code at `ORCHESTRATOR_MAX_REEVALUATIONS` (default 5) regardless of what the model asks for.
  - *Never auto-submit.* The wrapped scripts mail only the candidate, so business rule 1 holds by construction: the agent has no tool that can reach a recruiter.
- **Every run writes `digests/orchestrator_log_<YYYYMMDD_HHMM>.json`, and the log is committed**: mode, `stopped_reason`, every tool call and its result, usage, `fallback_used`, and the agent's summary and rationale. The decision agent stores a rationale per job; this is the same audit for run-level decisions. It adds nothing to the repo's exposure, since the job data it summarizes is already committed in the digests (a settled 2026-08-23 decision).
- **Cost arithmetic.** The conversation itself is ~3-8 calls per run; re-evaluation adds at most 5 jobs x ~2-5 calls. Worst case ~30 extra calls per run on top of the decision agent's ~150, bounded by the two caps rather than by the model's restraint.
- **New env vars, all read dynamically**: `ORCHESTRATION_MODE` (`rules` default | `agent`), `ORCHESTRATOR_MAX_ITERATIONS` (default 8), `ORCHESTRATOR_MAX_REEVALUATIONS` (default 5). Unchanged, and worth restating as in the decision layer: still Kimi only (`kimi-k2.6`), no new third-party dependencies, all tests mock the LLM.

## Private outcome signals (2026-08-24)

The candidate's own verdicts -- the jobs he dismissed and why, and his stated reason for each application -- now calibrate the scorer and inform follow-up drafts, without ever becoming public data.

- **What is recorded.** `agents/outcome_notes.py` keeps two lists: dismissals (company, title, a free-text note and a reason from a fixed category vocabulary -- `salary`, `tech_mismatch`, `company_culture`, `location`, `seniority`, `language`, `other`) and motivations (company, title, free-text reason for applying). Re-recording the same job replaces the entry -- a change of mind is an update, not a duplicate.
- **Where it lives, and why.** `tracker/outcome_notes.json`, gitignored, synced to CI as the `OUTCOME_NOTES_B64` secret and restored by the same tolerant base64 step as the profile. `tracker/jobs.db` and the dashboard are committed and therefore public -- they must never carry these signals. The notes reach the LLM only as prompt text at runtime, aggregated, never raw.
- **How it reaches the agents.** `job_evaluator.load_outcome_calibration()` appends the dismissal aggregate as a new paragraph after the outcome summary -- one change covering both the rules evaluator and the decision agent, which reuses the function. `followup_writer.build_followup_prompt()` adds one line with the candidate's own motivation for that application, so the follow-up can echo his real reason.
- **The failure contract.** Missing file, corrupt JSON, import error -- any notes problem degrades to exactly the pre-existing behavior: byte-identical calibration text, byte-identical follow-up prompt. A private-notes problem must never break a scoring run.
- **Recording and syncing.** `python agents/outcome_notes.py dismiss "<company>" "<title>" --category salary --note "..."` and `... motivate "<company>" "<title>" --note "..."` locally (`list`/`summary` to inspect), then `base64 -w0 tracker/outcome_notes.json | gh secret set OUTCOME_NOTES_B64`. The secret is optional: absent, CI warns and runs without the signals.

## Ingestion quality (2026-08-21 audit -- what the scorer is fed)

The scoring brain was audited on 2026-08-17; its *input* was audited on 2026-08-21, against the committed data. Three findings, all fixed, all pinned by `tests/test_ingestion_quality.py`:

- **89% of evaluations were blind.** 169 of the first 190 records in `data/history/` carry `insufficient_info: true`: e-mail alert cards (LinkedIn, Glassdoor, XING, jobs.ch) contain a title, a company, a tracking URL and *no description at all*, so Kimi scored them from six words of title and the low-confidence cap pinned them at REVIEW forever. Every APPLY in the whole history came from Adzuna, the one source that ships a description. `agents/description_enricher.py` now looks those postings up on Adzuna and attaches the real text before scoring. It is deliberately conservative -- a *wrong* description silently corrupts a score, which is worse than the blind score it is fixing -- so an unverified company or a non-exact title match is rejected rather than guessed. Watch the ratio: `job_evaluator` prints it per run and the digest carries it as `scored_title_only`.
- **One card was parsed as two jobs.** Alert e-mails wrap the whole card in an outer `<a>` and the title in an inner one, so the parser emitted both `"Junior AI & Knowledge Engineer"` and `"Junior AI & Knowledge Engineer Randstad Digital · Zurich, Switzerland (Hybrid) Easy Apply"`. Different titles, so the `(title, company)` dedup never saw them as the same posting: 36 of 187 distinct titles in history are one of these pairs, each costing a duplicate LLM call, and the clean variant carried neither company nor location. `_collapse_card_variants()` merges them, keeping the clean title and harvesting company/location out of the long variant's tail; `tidy_job_fields()` then strips the company prefix and trailing city that Glassdoor glues into its titles.
- **In-batch dedup was weaker than the hash applied one step later.** `utils.deduplicate_jobs` compared raw lowercased fields, so "Zürich" vs "Zurich, Switzerland" and "BLP Digital" vs "BLP Digital AG" both survived it and were caught only by the SQLite hash -- after the batch had already paid for them. It now uses the same normalization as `deduplicator.make_hash`, and when two records collide the one with the longer description wins (an alert card and the same posting from Adzuna are not equally useful), with missing fields backfilled from the loser.

## Code Patterns & Standards

- **No em dashes** in generated text: use commas, colons, or restructure
- **Error handling**: try-except on every API call; errors must stay visible (log to `digests/evaluation_errors.txt`), never silently swallowed
- **Security**: HTML-escape any job field before putting it in HTML (dashboard, emails); URLs must be http(s)-validated; never interpolate `${{ inputs.* }}` into workflow `run:` blocks (use `env:`)
- **Naming**: snake_case files. The data contract is English-only: `company`/`title`/`location`/`description`/`language`/`posted_at`. It used to be PT-BR (`empresa`/`titulo`/`localizacao`/`descricao`/`idioma`/`data_post`), normalized via `unified_ingestor.normalize_job_fields`; this was fully migrated to English, including the live `tracker/jobs.db` schema (via `ALTER TABLE ... RENAME COLUMN` in `init_db()`/`init_applications_table()`, safe to re-run) and every committed historical JSON file. Never reintroduce PT-BR field names or content anywhere in the pipeline.
- **Commits**: atomic, descriptive

## Business Rules (CRITICAL)

1. **NEVER submit an application without explicit user approval**
2. **Always ask before deleting or overwriting files**
3. **Deduplication**: hash of normalized company+title+location (accents transliterated, legal suffixes like AG/GmbH stripped), 21-day retention in SQLite; `utils.deduplicate_jobs` applies the same normalization in-batch. `agents/email_parser_local.py._strip_scraped_noise()` strips Glassdoor/LinkedIn job-card UI noise (rating, salary badge, apply CTA, "posted N ago" freshness label) from scraped title/company before hashing -- that noise used to change on every re-send of the same listing and silently defeated the hash, re-evaluating the same job with Kimi repeatedly (found ~19% of `seen_jobs` were this kind of duplicate). Two layers since 2026-08-25: the hash itself was strengthened (titles keyed via `normalize_title`, stripping board padding like '(80%-100%) - Zurich'), and `filter_new_jobs` adds a compatibility scan on hash miss (title identity + normalised location + `companies_compatible` -- aliases only via exact first-token-plus-initials; 'Swiss' near-misses and 'Unknown' never merge), the same rule the dashboard merge prototyped. Rows stored under the old hash were migrated once via `python src/deduplicator.py rehash-seen` (26 re-hashed, 3 collisions merged of 72).
4. **Scoring is input, not gospel**: user can override any decision
5. **Cost control**: `MAX_EVALUATIONS_PER_RUN=30` caps LLM calls per run; `ENRICH_MAX_LOOKUPS=12` caps the enricher's Adzuna calls. Adzuna's free tier is 100 calls/day and the pipeline runs twice: 18 search queries x 1 location x 2 runs (36) + up to 12 lookups x 2 runs (24) = 60/day. Adding queries or raising either cap means redoing that arithmetic. `EVALUATION_MODE=agent` multiplies the LLM side, not the Adzuna side: typically 5-6 calls per job against 1 (+2 borderline) in rules mode, so up to ~270 calls per run inside the same 30-job cap, ~540/day at two runs. `AGENT_MAX_ITERATIONS` (default 8, plus one reserved finalization call) bounds the loop. `ORCHESTRATION_MODE=agent` adds a bounded slice on top: ~3-8 calls for the run-level conversation plus at most `ORCHESTRATOR_MAX_REEVALUATIONS` (default 5) re-scored REVIEW jobs x ~2-5 calls each, worst ~30 extra calls per run, with `ORCHESTRATOR_MAX_ITERATIONS` (default 8) bounding the conversation. An orchestrator failure runs the legacy three-script chain automatically, so the floor is the old behavior, never a skipped run.
6. **Provider**: Kimi only. Do not switch the pipeline to Claude/OpenAI/etc.

`config/candidate_profile.json` is gitignored, so the candidate's role,
languages, permit and contact details live in exactly two places: one laptop
and one GitHub secret. Neither appears in a diff, and CI silently uses
whichever the secret happens to hold.

That went wrong on 2026-08-24. His title changed to "AI Software Engineer
Intern", the profile was updated, `CANDIDATE_PROFILE_B64.txt` was not, and

`gh secret set`. Nothing complained.

`agents/check_profile.py` now runs before anything is fetched or scored, in
both the daily pipeline and add-job, and exits 1 on a contradiction. It
treats the CV as the source of truth (a human wrote it, an employer reads

`cv_model.txt`; `role` matches `experience[0].title`; and the CEFR level in
`language_levels` agrees with the prose in `languages` -- that last one
because the prompt once said B1 while the CV said A2, turning a real German
gap into a soft mention.

When the profile changes, regenerate the secret from the file, never from the
stale `.txt`:

```bash
base64 -w0 config/candidate_profile.json | gh secret set CANDIDATE_PROFILE_B64
```
