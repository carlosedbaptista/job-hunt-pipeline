# Job Hunt Pipeline — CLAUDE.md

## Project Overview

**Goal**: Automated job search and evaluation pipeline for AI/Data internships in Switzerland (Zurich/Zug). Ingests jobs from Adzuna and Gmail alerts, deduplicates, scores fit with the Kimi LLM, and delivers a daily digest, dashboard and alerts.

**Runtime**: GitHub Actions, 2x/day (05:00 and 12:00 UTC). No local server.

**AI provider**: Kimi (Moonshot) API. This is a deliberate decision: do NOT migrate the pipeline to the Claude API or any other provider. Claude acts only as the development assistant on this codebase.

## Technical Stack (real, as deployed)

- **Language**: Python 3.11
- **LLM**: Kimi API, model `kimi-k2.6` (fallback configurable via `KIMI_MODEL_FALLBACK`). `moonshot-v1-*` and `kimi-k2.5` sunset on 2026-08-31, never use them.
- **Job sources**: Adzuna API (`agents/adzuna_ingestor.py`), Gmail IMAP with App Password (`src/email_ingestor.py`)
- **Storage**: SQLite `tracker/jobs.db` (seen jobs, dedup), JSON artifacts in `digests/` and `data/`
- **Evaluation history**: `data/history/evaluations_YYYYMMDD.json` (appended every run)
- **Dashboard**: static HTML generated by `src/dashboard.py`, published via GitHub Pages. Fully static (no backend/write path): shows an "Application" column joined from `tracker/jobs.db`'s `applications` table by normalized company+title. A REVIEW/APPLY job with no tracked record and 10+ days old is shown as "No action" -- inferred, not an explicit user action (marking every skipped job would be too much friction). Actually recording "applied" or a response still only happens via `.github/workflows/track-application.yml`.
- **Notifications**: Gmail SMTP (digest email + high-score alerts)
- **CI**: `.github/workflows/job-hunt-scheduler.yml` (daily pipeline), `.github/workflows/add-job.yml` (manual evaluation -- also generates CV/CL automatically when the match is >= `THRESHOLD_APPLY`, via the same `agents/doc_generator.generate_docs_for_job()` the daily pipeline uses), `.github/workflows/track-application.yml` (manual: record that you applied, or a recruiter response, via `agents/tracker_updater.py`)
- Re-running "Add Job" for a posting you already evaluated REPLACES the old record (matched by normalized company+title, same as the dedup hash) instead of appending a duplicate -- the old score/reasoning is gone once replaced, by design.
- **Known caveat -- Google Drive uploads silently fail as configured**: the Service Account path in `gdrive_uploader.py` can authenticate and read/list folders, but Google rejects any actual file upload with "Service Accounts do not have storage quota" (regular personal Drive, not a paid Workspace Shared Drive). `_get_drive_service()` tries OAuth2 first (`GDRIVE_REFRESH_TOKEN_B64`) and only falls back to the Service Account, so completing `python config/setup_oauth2.py` and setting that secret is the fix -- until then, every CV/CL upload attempt fails (caught, logged, generation itself still succeeds). Both doc-gen workflow steps also upload `generated_docs/` as a 90-day GitHub Actions artifact specifically because of this, so a failed Drive upload doesn't mean the PDFs are lost.

## Pipeline flow (as executed by CI)

1. `agents/adzuna_ingestor.py` — fetch Adzuna jobs (strips query strings from URLs: they embed the app_id)
2. `src/email_ingestor.py` — fetch Gmail alerts (IMAP UIDs, `continue-on-error`)
3. `agents/email_parser_local.py` — parse job emails locally (regex + BeautifulSoup, no API)
4. `src/unified_ingestor.py` — merge sources, in-batch dedup, then **cross-run dedup via `src/deduplicator.filter_new_jobs` (SQLite, 21-day retention)**
5. `agents/job_evaluator.py` — score each new job with Kimi (capped by `MAX_EVALUATIONS_PER_RUN`, default 30)
6. `src/week4_pipeline.py --digest-only` — build digest
7. `src/dashboard.py` — regenerate dashboard
8. `agents/doc_generator.py` — tailored CV/CL for APPLY jobs (continue-on-error)
9. `agents/high_score_alert.py` — alert once per job >= 85 (dedup in `digests/alerted_jobs.json`)
10. `agents/followup_sender.py` — for `applications` rows with no response after 7+ days, drafts a follow-up with Kimi and emails the **draft to the candidate** (`GMAIL_RECIPIENT`), never to the recruiter; the candidate reviews and forwards it manually (continue-on-error)
11. `agents/email_notifier.py` — send digest email
12. Commit `data/raw_jobs/`, `data/history/`, `digests/`, `tracker/jobs.db`

## Scoring

- Thresholds are defined ONCE in `src/utils.py`: `THRESHOLD_APPLY=80`, `THRESHOLD_REVIEW=70` (env-overridable). All consumers (evaluator, digest, dashboard, notifier, alerts) import from there. Never hardcode 80/70 elsewhere.
- `decision` is ALWAYS derived from `score` via `utils.decision_from_score()` in `job_evaluator.py` -- never trust the model's own freeform `decision` field, it regularly drifts from what its own score implies.
- `red_flags`/`concerns` always surface regardless of score tier (a real bug used to drop them for APPLY-tier jobs -- exactly where they matter most). Concerns that are hard eligibility blockers (e.g. an unmet language requirement) are prefixed `"Blocker: "` by the model; digest_generator.py renders those with `⛔` separately from soft notes -- don't lump them back into one undifferentiated list.
- **Language requirements**: candidate's German is B1 (`config/candidate_profile.json.languages` -- read this from the profile, never hardcode a language level in `job_evaluator.py`, that was a real bug). A role that HARD-requires fluent/native German (or any language beyond English) the candidate doesn't have is an auto-SKIP, no exception, regardless of how strong the rest of the match is -- distinct from a SOFT mention ("German is a plus"), which stays a minor signal. This is deliberate business logic (2026-08-17 decision): an otherwise-perfect job he's ineligible for is noise, not signal.
- API failures produce `decision: "ERROR"`, `score: null`. They are excluded from rankings and metrics and reported separately. NEVER assign a fabricated score on error (a fake 55 once polluted 8 weeks of history).
- If ALL evaluations in a run fail, the evaluator exits 1 to fail the workflow loudly (usually: no Kimi credits).
- `job_evaluator.py` asks the model for `detected_company`/`detected_title`/`detected_location` and backfills any field the caller left `"Unknown"` -- manually-added jobs (`add_job.py`) had no location-extraction logic at all before this.

## Code Patterns & Standards

- **No em dashes** in generated text: use commas, colons, or restructure
- **Error handling**: try-except on every API call; errors must stay visible (log to `digests/evaluation_errors.txt`), never silently swallowed
- **Security**: HTML-escape any job field before putting it in HTML (dashboard, emails); URLs must be http(s)-validated; never interpolate `${{ inputs.* }}` into workflow `run:` blocks (use `env:`)
- **Naming**: snake_case files. The data contract is English-only: `company`/`title`/`location`/`description`/`language`/`posted_at`. It used to be PT-BR (`empresa`/`titulo`/`localizacao`/`descricao`/`idioma`/`data_post`), normalized via `unified_ingestor.normalize_job_fields`; this was fully migrated to English, including the live `tracker/jobs.db` schema (via `ALTER TABLE ... RENAME COLUMN` in `init_db()`/`init_applications_table()`, safe to re-run) and every committed historical JSON file. Never reintroduce PT-BR field names or content anywhere in the pipeline.
- **Commits**: atomic, descriptive

## Business Rules (CRITICAL)

1. **NEVER submit an application without explicit user approval**
2. **Always ask before deleting or overwriting files**
3. **Deduplication**: hash of normalized company+title+location (accents transliterated, legal suffixes like AG/GmbH stripped), 21-day retention in SQLite. `agents/email_parser_local.py._strip_scraped_noise()` strips Glassdoor/LinkedIn job-card UI noise (rating, salary badge, apply CTA, "posted N ago" freshness label) from scraped title/company before hashing -- that noise used to change on every re-send of the same listing and silently defeated the hash, re-evaluating the same job with Kimi repeatedly (found ~19% of `seen_jobs` were this kind of duplicate).
4. **Scoring is input, not gospel**: user can override any decision
5. **Cost control**: `MAX_EVALUATIONS_PER_RUN=30` caps LLM calls per run
6. **Provider**: Kimi only. Do not switch the pipeline to Claude/OpenAI/etc.

## Security & Credentials

Never commit: `.env`, `config/candidate_profile.json`, `config/photo.*`, `config/cv_model.txt`, `config/cover_letter_model.txt`, `digests/raw_emails*.json`, GDrive credentials. These are restored in CI from base64 GitHub Secrets (`CANDIDATE_PROFILE_B64` etc.).

Secrets used by CI: `KIMI_API_KEY`, `KIMI_BASE_URL` (optional), `ADZUNA_APP_ID`, `ADZUNA_APP_KEY`, `GMAIL_SENDER`, `GMAIL_APP_PASSWORD`, `GMAIL_RECIPIENT`, `CANDIDATE_*_B64`, `GDRIVE_*`.

Known caveat: the repo is public. Everything committed (digests, dashboard, raw jobs, jobs.db) is world-readable; keep PII and credentials out. Adzuna URLs must have their query strings stripped before persisting (the `utm_source` param is the app_id).
