# Job Hunt Pipeline — CLAUDE.md

## Project Overview

**Goal**: Automated job search and evaluation pipeline for AI / Automation / Data Engineering roles in Switzerland (Zurich/Zug). Ingests jobs from Adzuna and Gmail alerts, deduplicates, fills in missing descriptions, scores fit with the Kimi LLM, and delivers a daily digest, dashboard and alerts.

**Runtime**: GitHub Actions, 2x/day (05:00 and 12:00 UTC). No local server.

**AI provider**: Kimi (Moonshot) API. This is a deliberate decision: do NOT migrate the pipeline to the Claude API or any other provider. Claude acts only as the development assistant on this codebase.

## Technical Stack (real, as deployed)

- **Language**: Python 3.11
- **LLM**: Kimi API, model `kimi-k2.6` (fallback configurable via `KIMI_MODEL_FALLBACK`). `moonshot-v1-*` and `kimi-k2.5` sunset on 2026-08-31, never use them.
- **Job sources**: Adzuna API (`agents/adzuna_ingestor.py`), Gmail IMAP with App Password (`src/email_ingestor.py`)
- **Storage**: SQLite `tracker/jobs.db` (seen jobs, dedup), JSON artifacts in `digests/` and `data/`
- **Evaluation history**: `data/history/evaluations_YYYYMMDD.json` (appended every run)
- **Dashboard**: static HTML generated by `src/dashboard.py`, published via GitHub Pages. Fully static (no backend/write path): shows an "Application" column joined from `tracker/jobs.db`'s `applications` table by normalized company+title. In-dashboard dedup is by normalized company+title (NOT URL -- the same posting arrives with different tracking URLs per source), and manual evaluations are merged FIRST so a manual re-evaluation always wins over the older history entry. A REVIEW/APPLY job with no tracked record and 10+ days old is shown as "No action" -- inferred, not an explicit user action (marking every skipped job would be too much friction). Actually recording "applied" or a response still only happens via `.github/workflows/track-application.yml`.
- **Notifications**: Gmail SMTP (digest email + high-score alerts)
- **Tests**: `tests/` (pytest, mocked LLM -- no API calls). `test_scoring_consistency.py` is the consistency suite born from the 2026-08-17 audit; `test_ingestion_quality.py` covers what the scorer is *fed* (alert-card parsing, in-batch dedup, description enrichment) and comes from the 2026-08-21 ingestion audit. Install with `pip install -r requirements-dev.txt`, run `python -m pytest tests/` before touching scoring, dedup or parsing logic -- and `.github/workflows/tests.yml` now runs it on every push and PR, so this is no longer on the honour system. `scripts/smoke_kimi_brain.py` (gitignored) re-probes the real model against 10 controlled synthetic postings when the prompt changes.
- **CI**: `.github/workflows/job-hunt-scheduler.yml` (daily pipeline), `.github/workflows/tests.yml` (pytest + `compileall` on push/PR, no secrets exposed), `.github/workflows/add-job.yml` (manual evaluation -- also generates CV/CL automatically when the match is >= `THRESHOLD_APPLY`, via the same `agents/doc_generator.generate_docs_for_job()` the daily pipeline uses), `.github/workflows/track-application.yml` (manual: record that you applied, or a recruiter response, via `agents/tracker_updater.py`)
- Re-running "Add Job" for a posting you already evaluated REPLACES the old record (matched by normalized company+title, same as the dedup hash) instead of appending a duplicate -- the old score/reasoning is gone once replaced, by design.
- **How a generated CV/CL reaches the candidate -- by e-mail, not Drive**: `doc_generator` attaches both PDFs and mails them to `GMAIL_RECIPIENT` (`_email_docs_to_candidate`, reusing `email_notifier.send_email(..., attachments=[...])`). It goes to the candidate only, never a recruiter, so the "never submit without approval" rule holds. This exists because the two alternatives are both closed: the repo is PUBLIC so the PDFs can be neither committed nor uploaded as an Actions artifact (a 90-day artifact on a public repo is downloadable by any authenticated GitHub user, and the PDFs carry name, phone, e-mail, LinkedIn, permit and photo -- that upload was REMOVED), and Google Drive has never worked. Verified again on 2026-08-23: without the e-mail path a generated document died with the runner.
- **Google Drive works, via OAuth2 with the `drive.file` scope** (set up 2026-08-23). The Service Account path is dead by construction and kept only as a fallback: Google reports a Service Account's quota as `{"limit": "0"}`, so it owns no bytes and every upload into a personal Drive answers 403 `storageQuotaExceeded`. Sharing the folder with it grants the right to enter, never to store; only a paid Workspace Shared Drive would work. OAuth2 makes the candidate the owner (15 GB). The scope is `drive.file`, NOT `drive`, because the refresh token lives in a GitHub Secret: a leak then costs the job PDFs he already sends to recruiters instead of his entire personal Drive. Consequence to remember: **a folder created by hand in the browser is invisible to the app**, so `_resolve_root_folder()` probes `GDRIVE_PARENT_FOLDER_ID` for reachability and falls back to finding-or-creating its own `GDRIVE_ROOT_FOLDER_NAME` root. Structure is `Job Hunt Pipeline / {Company} - {Title} / CV+CL`. `config/oauth2_client_secret.json` (gitignored) and `GDRIVE_REFRESH_TOKEN_B64` are what make it run; re-mint both with `python config/setup_oauth2.py`.

## Pipeline flow (as executed by CI)

1. `agents/adzuna_ingestor.py` — fetch Adzuna jobs (strips query strings from URLs: they embed the app_id). 18 queries against ONE location (Zurich) with `ADZUNA_DISTANCE_KM=30`, which reaches Zug and Winterthur in the same call. The Zurich+Zug pass it replaced spent half the free tier on Zug for 4 distinct jobs in 84 days (measured 2026-08-23). `results_per_page` is Adzuna's maximum of 50: page size does not change the call count. Budget: 18 x 1 x 2 runs = 36/day, plus up to 24 from the enricher, against a free tier of 100 — `tests/test_adzuna_targeting.py` asserts this, so redo the arithmetic there before adding a query or a location.. Queries are overridable via `ADZUNA_QUERIES`; keep the list at 12 or redo the quota arithmetic in the comment there
2. `src/email_ingestor.py` — fetch Gmail alerts (IMAP UIDs, `continue-on-error`)
3. `agents/email_parser_local.py` — parse job emails locally (regex + BeautifulSoup, no API)
4. `src/unified_ingestor.py` — merge sources, in-batch dedup, then **cross-run dedup via `src/deduplicator.filter_new_jobs` (SQLite, 21-day retention)**. The cost cap is applied HERE, before marking: jobs beyond `MAX_EVALUATIONS_PER_RUN` stay *unseen* and resurface next run as a queue (pre-audit behaviour marked everything seen and silently swallowed jobs 31+ forever)
5. `agents/description_enricher.py` — for jobs still under `MIN_DESCRIPTION_CHARS`, look the same posting up on Adzuna and attach the real description (`continue-on-error`; budget `ENRICH_MAX_LOOKUPS`, default 12)
6. `agents/job_evaluator.py` — score each new job with Kimi (capped by `MAX_EVALUATIONS_PER_RUN`, default 30)
7. `src/week4_pipeline.py --digest-only` — build digest
8. `src/dashboard.py` — regenerate dashboard
9. `agents/doc_generator.py` — tailored CV/CL for APPLY jobs, mailed to the candidate as attachments (continue-on-error). Prints a one-line count even when nothing qualifies: silence in that step used to be indistinguishable from a crash.
10. `agents/high_score_alert.py` — alert once per job >= 85 (dedup in `digests/alerted_jobs.json`)
11. `agents/followup_sender.py` — for `applications` rows with no response after 7+ days, drafts a follow-up with Kimi and emails the **draft to the candidate** (`GMAIL_RECIPIENT`), never to the recruiter; the candidate reviews and forwards it manually (continue-on-error)
12. `agents/email_notifier.py` — send digest email
13. Commit `data/raw_jobs/`, `data/history/`, `digests/` -- and `tracker/jobs.db` **only when the evaluator step succeeded**. `unified_ingestor` marks jobs seen BEFORE scoring, so committing the DB after a failed evaluation (no Kimi credits) would suppress those jobs for the whole 21-day retention: a billing lapse silently destroying three weeks of discovery. All three pushing workflows share the `job-hunt-repo-write` concurrency group (jobs.db is binary and cannot be merged) and push with rebase-and-retry.

## Maintenance tools

- `agents/rescore_history.py` brings already-stored evaluations up to date when the rules change. Deterministic pass (free) re-derives `insufficient_info`, `language_gap_intermediate` and the decision from stored text; `--full` re-scores with the LLM (one call per job, `--limit`); `--reset-seen` clears unapplied `seen_jobs` rows so those postings re-enter the pipeline and get enriched and re-scored properly. Dry run by default, `--apply` to write. Note for this repo's current state: the deterministic pass changes 0 of 190 records, because 169 have no posting text to re-derive from -- re-ingestion is the only real fix for them.
- **Never commit CV/CL PDFs as workflow artifacts.** This repo is public and Actions artifacts are downloadable by any authenticated GitHub user; the generated documents carry name, phone, personal e-mail, permit and photo. Google Drive (OAuth2) is the intended durable copy.
- `config/cv_model.txt` and `config/cover_letter_model.txt` (restored from `CV_MODEL_B64` / `CL_MODEL_B64`) are the prose reference for generated documents. They were restored and then read by nothing until `doc_generator._load_text_model` started feeding the cover-letter model into the prompt as a voice reference.

## Scoring Philosophy (the why -- not obvious from code alone)

- **Role shape beats checklist match.** Ownership from day one, building vs. maintaining, hands-on agentic-AI work matter more than a perfect skills/domain checklist. Calibration anchor: the 'AI Platform Engineer Intern' at a small regulated investment firm, rated 100/APPLY by the candidate himself.
- **Deliberate career changer, open to unfamiliar domains** (finance, healthcare, retail): lack of domain experience is a soft gap, never a penalty when the technical/functional role matches.
- **Hard requirements are NOT domain gaps.** A mandatory fluent/native language beyond English (his German level lives in `language_levels`; A2 as of 2026-08-23), wrong permit, or ineligible location is a hard eligibility blocker -> automatic SKIP, no exception, however strong the rest of the match. An otherwise-perfect job he's disqualified from is noise, not signal. A soft mention ('German is a plus', up to B1 acceptable) is a minor signal, never a blocker. The INTERMEDIATE zone ('working/professional proficiency' -- every CEFR level above his own and below C1, derived by `utils.levels_above`, so B1 and B2 at A2) is neither: never a blocker, but APPLY is capped at REVIEW so he judges case by case and the system never auto-generates CV/CL for it (2026-08-17 product decision).
- **The score is the source of truth for ranking, but decisions are always derived locally, never trusted from the model's freeform field** -- and a real hard blocker caps the decision at SKIP regardless of score (the score stays visible for information).
- **Concerns surface at every tier, with correct severity**: real blockers render with ⛔ and the "Blocker: " prefix; minor notes get light visual weight. Never lump them together.
- **Scoring is input, not gospel**: the user can override any decision (manual re-evaluation replaces the record).

## Scoring (mechanics)

- Thresholds are defined ONCE in `src/utils.py`: `THRESHOLD_APPLY=80`, `THRESHOLD_REVIEW=70` (env-overridable). All consumers import from there. Never hardcode 80/70 elsewhere.
- Every consumer derives the decision via `utils.effective_decision(ev)` (evaluator, digest, alerts, doc_generator; the dashboard gets it precomputed per job as `_has_blocker`/`_insufficient`/`_lang_gap`): thresholds on the sanitized score, then the hard-blocker lock, then the low-confidence caps (`insufficient_info`, description < 200 chars; `language_gap_intermediate`, the B2/working-proficiency zone -- both cap APPLY at REVIEW so neither a bare title nor an above-his-level language ask ever auto-generates CV/CL).
- The model returns a structured `hard_blockers` list separate from soft `concerns` ('Blocker: '-prefixed concerns remain as the backward-compat path for old records). Spurious "Blocker: None ..." entries are filtered by `utils.is_spurious_blocker` -- the model uses the prefix even to say there is NO blocker, and taking it literally would SKIP the best jobs.
- `agents/job_evaluator.py` scans the FULL description deterministically in two tiers (`detect_language_requirement_tier`: hard = fluent/native/C1-C2/verhandlungssicher; intermediate = working/professional proficiency, B2) and injects the evidence snippet into the prompt with tier-appropriate instructions. Postings longer than the window are excerpted head(2/3)+tail(1/3) via `_excerpt()` -- Swiss requirement blocks live at the END of long postings: before the 2026-08-17 audit the window was a 1500-char head, and a C1-German clause past char 1500 invisibly flipped an auto-SKIP job to 96/APPLY; later the same day a 'working proficiency in German' clause past char 4000 let a job score 92/APPLY with zero language signal.
- The prompt includes today's date (grounds timeline reasoning: notice period vs start date -- the model once invented a "16+ months away" blocker for a start 2 months out) and counts fully-remote-within-Switzerland as Zurich-area.
- Score sanitisation: coerced to int, clamped to 0-100 (a string "85" used to crash into ERROR; 120 passed as APPLY). A missing/unparseable score is an ERROR, never a silent default 50. API failures produce `decision: "ERROR"`, `score: null`, excluded from rankings and metrics, reported separately. NEVER fabricate a score.
- If ALL evaluations in a run fail, the evaluator exits 1 to fail the workflow loudly (usually: no Kimi credits). Same if `config/candidate_profile.json` is missing/invalid: main() exits 1 rather than silently scoring the whole run against the generic fallback profile.
- **Language calibration is derived, never hardcoded.** `candidate_profile.json` carries `language_levels` (e.g. `{"german": "A2"}`); `utils.candidate_language_level` reads it and `utils.levels_above` computes the intermediate band as *every CEFR level above his own and below C1*. For A2 that is B1 and B2; at B1 it narrows to B2 alone. The prompt text, the pipeline-note wording and the deterministic tier regex all interpolate from it. This closed a real regression: the prompt said "his German is B1" while the CV said A2, and the intermediate band was the fixed set `{B2}`, so a "German B1 required" posting read as a *soft* mention when it was a genuine gap. An unset level falls back to the weakest, which over-reports gaps rather than hiding them -- the safe direction.
- **The scorer sees the target role, not just the current one.** `target_role` in the profile is injected as "Looking for (score fit to THIS, not to his current job)". Without it the model matched postings against his current job title, which is precisely what he is trying to move on from.
- `job_evaluator.py` asks the model for `detected_company`/`detected_title`/`detected_location` and backfills any field the caller left `"Unknown"` -- manually-added jobs (`add_job.py`) had no location-extraction logic at all before this.

## Ingestion quality (2026-08-21 audit -- what the scorer is fed)

The scoring brain was audited on 2026-08-17; its *input* was audited on 2026-08-21, against the committed data. Three findings, all fixed, all pinned by `tests/test_ingestion_quality.py`:

- **89% of evaluations were blind.** 169 of the first 190 records in `data/history/` carry `insufficient_info: true`: e-mail alert cards (LinkedIn, Glassdoor, XING, jobs.ch) contain a title, a company, a tracking URL and *no description at all*, so Kimi scored them from six words of title and the low-confidence cap pinned them at REVIEW forever. Every APPLY in the whole history came from Adzuna, the one source that ships a description. `agents/description_enricher.py` now looks those postings up on Adzuna and attaches the real text before scoring. It is deliberately conservative -- a *wrong* description silently corrupts a score, which is worse than the blind score it is fixing -- so an unverified company or a non-exact title match is rejected rather than guessed. Watch the ratio: `job_evaluator` prints it per run and the digest carries it as `scored_title_only`.
- **One card was parsed as two jobs.** Alert e-mails wrap the whole card in an outer `<a>` and the title in an inner one, so the parser emitted both `"Junior AI & Knowledge Engineer"` and `"Junior AI & Knowledge Engineer Randstad Digital · Zurich, Switzerland (Hybrid) Easy Apply"`. Different titles, so the `(title, company)` dedup never saw them as the same posting: 36 of 187 distinct titles in history are one of these pairs, each costing a duplicate LLM call, and the clean variant carried neither company nor location. `_collapse_card_variants()` merges them, keeping the clean title and harvesting company/location out of the long variant's tail; `tidy_job_fields()` then strips the company prefix and trailing city that Glassdoor glues into its titles.
- **In-batch dedup was weaker than the hash applied one step later.** `utils.deduplicate_jobs` compared raw lowercased fields, so "Zürich" vs "Zurich, Switzerland" and "BLP Digital" vs "BLP Digital AG" both survived it and were caught only by the SQLite hash -- after the batch had already paid for them. It now uses the same normalization as `deduplicator.make_hash`, and when two records collide the one with the longer description wins (an alert card and the same posting from Adzuna are not equally useful), with missing fields backfilled from the loser.

## Code Patterns & Standards

- **No em dashes** in generated text: use commas, colons, or restructure
- **Error handling**: try-except on every API call; errors must stay visible (log to `digests/evaluation_errors.txt`), never silently swallowed
- **Security**: HTML-escape any job field before putting it in HTML (dashboard, emails); URLs must be http(s)-validated; never interpolate `${{ inputs.* }}` into workflow `run:` blocks (use `env:`)
- **Naming**: snake_case files. The data contract is English-only: `company`/`title`/`location`/`description`/`language`/`posted_at`. It used to be PT-BR (`empresa`/`titulo`/`localizacao`/`descricao`/`idioma`/`data_post`), normalized via `unified_ingestor.normalize_job_fields`; this was fully migrated to English, including the live `tracker/jobs.db` schema (via `ALTER TABLE ... RENAME COLUMN` in `init_db()`/`init_applications_table()`, safe to re-run) and every committed historical JSON file. Never reintroduce PT-BR field names or content anywhere in the pipeline.
- **Commits**: atomic, descriptive

## Business Rules (CRITICAL)

1. **NEVER submit an application without explicit user approval**
2. **Always ask before deleting or overwriting files**
3. **Deduplication**: hash of normalized company+title+location (accents transliterated, legal suffixes like AG/GmbH stripped), 21-day retention in SQLite; `utils.deduplicate_jobs` applies the same normalization in-batch. `agents/email_parser_local.py._strip_scraped_noise()` strips Glassdoor/LinkedIn job-card UI noise (rating, salary badge, apply CTA, "posted N ago" freshness label) from scraped title/company before hashing -- that noise used to change on every re-send of the same listing and silently defeated the hash, re-evaluating the same job with Kimi repeatedly (found ~19% of `seen_jobs` were this kind of duplicate).
4. **Scoring is input, not gospel**: user can override any decision
5. **Cost control**: `MAX_EVALUATIONS_PER_RUN=30` caps LLM calls per run; `ENRICH_MAX_LOOKUPS=12` caps the enricher's Adzuna calls. Adzuna's free tier is 100 calls/day and the pipeline runs twice: 12 search queries x 2 locations x 2 runs (48) + 12 lookups x 2 runs (24) = 72/day. Adding queries or raising either cap means redoing that arithmetic.
6. **Provider**: Kimi only. Do not switch the pipeline to Claude/OpenAI/etc.

## Security & Credentials

Never commit: `.env`, `config/candidate_profile.json`, `config/photo.*`, `config/cv_model.txt`, `config/cover_letter_model.txt`, `digests/raw_emails*.json`, GDrive credentials. These are restored in CI from base64 GitHub Secrets (`CANDIDATE_PROFILE_B64` etc.).

Secrets used by CI: `KIMI_API_KEY`, `KIMI_BASE_URL` (optional), `ADZUNA_APP_ID`, `ADZUNA_APP_KEY`, `GMAIL_SENDER`, `GMAIL_APP_PASSWORD`, `GMAIL_RECIPIENT`, `CANDIDATE_*_B64`, `GDRIVE_*`.

Known caveat: the repo is public. Everything committed (digests, dashboard, raw jobs, jobs.db) is world-readable; keep PII and credentials out. Adzuna URLs must have their query strings stripped before persisting (the `utm_source` param is the app_id).
